# Tofu gallery copy

This repository is Tofu's copy of **thedevs-network/kutt** (licence: MIT), listed in Tofu's app gallery as **Kutt**: short links with click counts, on your own address.

- `main` mirrors the upstream repository and is never committed to by Tofu.
- `tofu` carries Tofu's own changes; tags named `pin/<date>` mark the versions the gallery points to. The current pin is `pin/2026-10-27`.
- A visitor who chooses this app gets a private snapshot of the pinned version in their own Tofu account. Their copy does not follow upstream updates.
- Upstream: https://github.com/thedevs-network/kutt at `029da42b2459693681886665589fd9512d6b473c` (2026-10-19, package version 3.2.6).

## How Tofu runs it

- Framework preset `container`, root folder: the repository root. Tofu builds the root `Dockerfile` and runs the image as a service, so there is no separate install command, build command or output directory.
- The `Dockerfile` (Node 22 on Alpine) runs `npm ci --omit=dev`, then starts with `node server/tofu-migrate.js && npm start`: the schema step runs Kutt's migrations (`server/migrations`, through knex) and turns row-level security on for Kutt's tables, then `node server/server.js --production` starts the server. It listens on `PORT`, which Tofu sets (80 unless the app has a `PORT` setting). The image has no `USER` line, so the server runs as root, which port 80 needs.
- Database: PostgreSQL, the app's own Tofu database, read from `DATABASE_URL`. Kutt makes and updates its own tables at every start (knex keeps its record in `knex_migrations`), one start at a time (see "Start-up when several starts run at once"). There is no `supabase/migrations` folder, so Tofu applies no migration files for this app.
- Settings Tofu saves for a copy: `DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_ANON_KEY` and `SUPABASE_CA_CERT` (the database), and `DEFAULT_DOMAIN`, which the gallery sets to the copy's own address. Nothing has to be typed before the first deploy. The image sets `NODE_ENV=production` and `CUSTOM_DOMAIN_USE_HTTPS=true`.
- One hidden value the owner saves after the first deploy: `ADMIN_SETUP_PASSWORD` (see "The first account").
- Settings an owner may add later: `SITE_NAME`; mail (`MAIL_ENABLED=true`, `MAIL_HOST`, `MAIL_PORT`, `MAIL_SECURE`, `MAIL_USER`, `MAIL_FROM`, and `MAIL_PASSWORD` as a hidden value); `REPORT_EMAIL` and `CONTACT_EMAIL`; `ENABLE_RATE_LIMIT=true`; their own `JWT_SECRET` (hidden, see "The sign-in secret"); sign-in with an identity provider (`OIDC_*`, with `OIDC_CLIENT_SECRET` hidden).
- Redis stays off (`REDIS_ENABLED=false`, upstream's default): visits are counted inside the server process, and rate limits, when turned on, are kept in its memory.

## What Tofu changes

Each change is a `Tofu: ...` commit on `tofu` whose message gives its reason.

- `server/tofu-migrate.js` (new, Tofu's own file): the schema step the image's `CMD` runs before `npm start`, in place of upstream's `npm run migrate` (`knex migrate:latest`). It uses upstream's `knexfile.js` and migrations, and `server/tofu.js` (`prepareDatabase`) for the rest; it exits with 1 if the step fails, and then the server is not started. `npm run migrate` is still in `package.json`, as upstream has it, and the image does not use it.
- `server/tofu.js` (new, Tofu's own file). Everything below that is more than a line lives here, and it is called from:
  - `server/env.js`, before Kutt reads its settings:
    - **`DATABASE_URL`** (`postgres://` or `postgresql://`) fills `DB_CLIENT=pg` and each of `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` (decoded), `DB_SSL` that is not set. Kutt has no setting that takes a URL, and without one it falls back to SQLite in `db/data`, which loses every link at each restart on hosting without a disk. A `DB_*` setting the owner sets is kept.
    - **TLS.** `DATABASE_URL`'s `sslmode` decides `DB_SSL` and the new `DB_SSL_REJECT_UNAUTHORIZED`: `disable` and `allow` connect without TLS; `prefer`, `require` and `no-verify` encrypt; `verify-ca` and `verify-full` also check the certificate. The new `DB_SSL_CA` is filled from `SUPABASE_CA_CERT`, the database's certificate, which Tofu saves beside `DATABASE_URL`.
    - **`JWT_SECRET`** is derived from `DATABASE_URL` when it is not set (see "The sign-in secret").
    - **`DEFAULT_DOMAIN`** given as an address (`https://<name>.trytofu.app`, as the gallery saves it) is read as its host. Kutt builds every short link as `https://<DEFAULT_DOMAIN>/<address>`.
  - `knexfile.js` (the migrations) and `server/knex.js` (the server) take their TLS option from it. Upstream passes `DB_SSL=true` to node-postgres as it is, which checks the server's certificate against Node's own list of authorities, and a managed database's pooler does not pass that. Now: checked against `DB_SSL_CA` when there is one; encrypted without checking when there is none and `DB_SSL_REJECT_UNAUTHORIZED=false`; as upstream otherwise.
  - `server/tofu-migrate.js`: the schema step (see "Start-up when several starts run at once" and "Kutt's tables and Supabase's Data API").
  - `server/handlers/auth.handler.js`, `server/handlers/locals.handler.js` and `server/views/partials/auth/form_admin.hbs`: the setup password for the first account (see "The first account").
  - `server/env.js` also declares the three new settings, `DB_SSL_REJECT_UNAUTHORIZED` (default `true`), `DB_SSL_CA` and `ADMIN_SETUP_PASSWORD`.
- `server/handlers/auth.handler.js` also signs the owner in once the admin account is made. Upstream signs the new account's sign-in token with what it inserted, which has no account id, so the token has no `sub`, Kutt's own sign-in check refuses it (`server/passport.js`), and the new administrator lands on the sign-in form. Now the token is signed for the stored account. This is upstream Kutt 3.2.6's code, unchanged on upstream's main.
- `Dockerfile`:
  - `package.json` and `package-lock.json` are copied in with `COPY` instead of bind-mounted for `npm ci`. Tofu's container hosting builds with buildah, not Docker's BuildKit, and a cache mount is the one `RUN --mount` form a gallery image has been built with there so far (HomeBox's). The cache mount stays.
  - `ENV CUSTOM_DOMAIN_USE_HTTPS=true`: a domain connected to the app on Tofu is served over HTTPS, so short links on a custom domain start with `https://`. The owner can set it back to `false`.
  - `CMD` runs `node server/tofu-migrate.js` instead of `npm run migrate` before `npm start`.
- `server/server.js` is upstream's file again. The pins of 2026-10-25 turned row-level security on there, after the migrations had already been committed; that now happens inside the schema step.
- `server/views/partials/settings/domain/index.hbs`: Settings > Custom domain told people to point their domain's A record at "our IP address", which a copy on Tofu does not have. With neither `SERVER_IP_ADDRESS` nor `SERVER_CNAME_ADDRESS` set, it now says to connect the domain on the app's Domains page in Tofu first. With either set, the text is upstream's.
- `.example.env` names the new settings.
- No file was removed. Upstream's three GitHub Actions workflows (Docker image builds) stay; a copy never runs them.

## The first account

A new Kutt has no account. Its first visitor is sent to `/create-admin`, and the account made there is the administrator. A copy is online at a public address before its owner first opens it, so on Tofu that page only completes with the setup password:

1. After the first deploy, the owner opens the app's **Keys & settings** page in Tofu, saves `ADMIN_SETUP_PASSWORD` with **Hide this value after saving** turned on (at least 12 characters; a long random one is best, for example the output of `openssl rand -base64 24`), and deploys again.
2. The owner opens the copy, which shows "Create an Admin account first", and enters their email address, a password for the account, and the setup password.
3. The page says "Welcome. Redirecting to homepage..." and opens the homepage signed in to the new administrator account, with **Admin** and **Settings** in the header. (Upstream Kutt 3.2.6 does not sign the new account in at this step, so its owner sees the sign-in form and signs in again; this copy does, see "What Tofu changes".)

- Until `ADMIN_SETUP_PASSWORD` is saved, the page explains this and shows no form, and a request to create the account (`POST /api/auth/create-admin`, also as `/api/v2/...`) is refused. A saved value shorter than 12 characters is refused the same way.
- Wrong setup passwords are counted per visitor address: after ten wrong ones in ten minutes from one address, every attempt from that address, the right one included, is refused until the oldest of those ten is more than ten minutes old. Other addresses are not affected, so a stranger guessing from another address cannot make the owner wait, as anyone could with the pins before 2026-10-27, which counted wrong answers for the whole server. A stranger who shares the owner's address still can, for example someone on the same home or office network, behind the same mobile carrier's or VPN's shared address, or in the same IPv6 /64. Making the app private on Tofu until the account exists keeps strangers from guessing at all.
  - The address is the last entry of `X-Forwarded-For`, the one the nearest proxy wrote, or the connection's own address when that header is missing or its last entry is not an address. IPv6 addresses are counted by their /64, and `::ffff:1.2.3.4` as `1.2.3.4`. Where nothing in front of Kutt writes that header, a visitor can send their own and choose the address they are counted under.
  - On Tofu that entry is the visitor's own address and the only one: measured on 2026-10-27 with a test container, Tofu's container hosting replaced `X-Forwarded-For`, `X-Real-IP`, `X-Vercel-Forwarded-For` and `Forwarded` with the visitor's address whatever the visitor sent in them, and the connection the app saw came from a local proxy at 127.0.0.1.
  - The counts are kept in the server's memory for at most 1,000 addresses. Past that, the address whose last wrong answer is oldest is forgotten, so the count stops one guesser, not a crowd: someone who takes turns among more than 1,000 addresses (or IPv6 /64s, of which one /48 holds 65,536) is never refused, because each one is forgotten before its second wrong answer. In a check with a stopped clock, 50 rounds of one wrong answer from each of 1,000 addresses had 10,000 answers compared with the setup password and 40,000 refused, and with 1,001 addresses all 50,050 were compared and none refused; the pins before 2026-10-27 compared 10 in all. A long random setup password is what protects a copy then. A restart clears the counts.
- Once any account exists, the page sends people to the sign-in page, and the setup password is never read again. Changing or removing it later changes nothing.
- Sign-up is closed: `DISALLOW_REGISTRATION` is `true` by default, and sign-up also needs mail, which is off. The administrator adds the other people under **Admin > Users > Create user** (keep **Verified** ticked, as it is by default). Making links needs an account: `DISALLOW_ANONYMOUS_LINKS` is `true` by default, and an owner should keep it so on a public address.

## The sign-in secret

Kutt signs every sign-in cookie with `JWT_SECRET` and does not start in production without one.

- When `JWT_SECRET` is not set and `DATABASE_URL` is, it is the SHA-256 of `kutt-jwt-secret:` followed by the whole `DATABASE_URL`, as 64 hex characters, worked out at every start. It is only as secret as `DATABASE_URL`, which Tofu keeps as a hidden value.
- Anything that changes `DATABASE_URL` (a new database password, another host or pooler address, other options, a database brought back under another address) changes it at the next start, and everyone has to sign in again. Links, visits, accounts and API keys are not affected: API keys are kept in the database.
- To keep sign-ins across such a change, save your own `JWT_SECRET` as a hidden value (a long random string) and keep it unchanged. Saving it signs everyone out once.

## Kutt's tables and Supabase's Data API

Tofu's databases are Supabase PostgreSQL. On a database whose default privileges still give every new table in `public` to the Data API's roles (`anon` and `authenticated`), which is every Tofu database created before 2026-10-30, anyone with the project's public key could read and change Kutt's tables through the Data API: `users`, with password hashes and API keys, included.

- At every start, in the schema step and inside its transaction, so that a new database's tables are never committed without it, Kutt turns row-level security on, with no policy, for its own tables that do not have it yet: `users`, `ips`, `domains`, `hosts`, `links`, `visits`, `knex_migrations` and `knex_migrations_lock`, where its own role owns them. These are every table Kutt makes; its role owns no other table and no schema. The log says `> Turned on row-level security on 8 of Kutt's tables for Supabase's Data API` at the first start and nothing at later ones.
- With row-level security on and no policy, those roles see no row and can change nothing. Kutt's own connection owns the tables, so it is not limited.
- It never turns row-level security off, touches no other table, and does nothing on a database without those roles. Its changes wait at most 5 seconds for a table another connection is using. If they fail, the schema step fails, and that start exits instead of serving with open tables; a later start tries again. (The pins of 2026-10-25 logged a warning and started anyway.)

## Start-up when several starts run at once

Tofu's container hosting can start a new deployment several times within a second or two, each start on its own, all with the same database. Upstream's `knex migrate:latest` takes knex's own migration lock (a row in `knex_migrations_lock`) only after it has made `knex_migrations`, `knex_migrations_lock` and that row without any lock, so on an empty database such starts collide while making them, and every start but one exits before its server starts (see Verification).

- **Where:** `server/tofu.js`, `prepareDatabase`, run by `server/tofu-migrate.js` from the image's `CMD` before `npm start`.
- **Which connection, which lock:** the step is one transaction on Kutt's ordinary database connection, `DATABASE_URL` (Tofu's transaction pooler, port 6543). It sets `lock_timeout` to 120 s and `statement_timeout` to 150 s for that transaction only, then takes `pg_advisory_xact_lock(1802859636)` (the bytes of "kutt", the same number in every start) before it reads or changes anything. In the same transaction it runs knex's migrations (knex makes its tables and lock row, lists the migrations already run, and runs the rest), then turns row-level security on, then commits.
- **Why it holds through the transaction pooler:** a transaction pooler lends a client one server connection from `BEGIN` to `COMMIT` or `ROLLBACK`, and a transaction-level advisory lock belongs to that transaction, so it is held for exactly the schema step and let go when the step ends, also when a start dies (its transaction is rolled back). PostgreSQL's DDL is transactional, so another start sees either none of the step's work or all of it. A session-level lock (`pg_advisory_lock`) is not used: it would stay with a server connection the pooler lends to other clients after the transaction.
- **A start that waits** waits at most 120 seconds, then reads the database again inside the lock. It finds the migrations already run and the tables already protected, so it logs `> Waited 3.3 s while another start prepared the database` and `> Already up to date`, and starts the server. After 120 seconds without the lock, the step fails with `canceling statement due to lock timeout`, makes nothing, and the start exits with 1. A shorter `statement_timeout` set on the database role does not cut the wait short.
- **An error about an object that already exists** (SQLSTATE 42P07, 42710, 42701, 42P06, 42723 or 23505), which could only come from something outside this lock changing the schema at the same moment, runs the whole step once more; a second one fails it.
- **How long:** through a stand-in for a transaction pooler that delays every message 15 ms each way, the first start on an empty database sent 88 statements in its schema step (3.3 s) and 93 up to its first HTTP 200, 4.2 s after it was started. A later start's step sends 19 statements (0.8 s). Five starts at once all answered 200, after 3.7 to 5.6 s.

## What works differently on Tofu

- **No email by default.** Email verification, password reset, changing an account's email address and the abuse-report form need mail settings (`MAIL_*`), which a copy does not have. Without them, a forgotten password cannot be reset from the app: to reset one, add mail settings and deploy again, then use "Forgot password?".
- **Custom domains.** Connect the domain on the app's Domains page in Tofu first. Then either set `DEFAULT_DOMAIN` to it and deploy again, so all short links use it, or add it under Kutt's **Settings > Custom domain**, so links can choose it. A custom domain added there can also name a homepage, where Kutt sends visitors who open the domain's bare address.
- **Visitor countries** come from the `CF-IPCountry` request header when a visit carries one, and otherwise from the GeoLite data geoip-lite ships with, looked up for the first address in `X-Forwarded-For` (`TRUST_PROXY=true`, upstream's default). geoip-lite's README asks for that data to be updated with a MaxMind licence key; a copy never updates it, so addresses in ranges assigned since may show as "Unknown" or a wrong country. geoip-lite 2.0.2 declares Node 24 or newer; the image uses Node 22, as upstream's does, and lookups worked on Node 22 here.
- **Expired links** are deleted by a timer inside the running server every 30 seconds.
- **Safari** visits are counted as browser "Other" (upstream).
- **The homepage logs one script error** on every load, `Cannot read properties of null (reading 'style')` at `onSearchInputLoad` in `static/scripts/main.js`: upstream's code, unchanged here. Signing in on `/login` also logs an htmx swap error, `Cannot read properties of null (reading 'insertBefore')`, in upstream's sign-in page, which Tofu does not change; `pin/2026-10-25.1` logs the same. Nothing visible breaks: the homepage opens signed in.
- The header's GitHub link, the footer's "Powered by Kutt" and the API key panel's link to `docs.kutt.to` lead to upstream, as upstream has them.

### `pin/2026-10-26`: several starts at once
